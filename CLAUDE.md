## Architecture

**NCM Paint Center** is a Laravel 13 paint retail platform with two interfaces:
- **Admin panel** at `/admin` — Filament 4.0 for inventory, orders, messages, reports
- **REST API** at `/api` — Sanctum-authenticated endpoints for mobile/web clients

**Related project:** The customer-facing mobile app lives at `C:\laragon\www\paintcenter-mobile`. It consumes this project's REST API (`/api`) and is developed separately. When making API changes (routes, response shapes, auth), consider the impact on that client.

**Stack:** PHP 8.3+, Laravel 13, Filament 4.0, MySQL 8.4 (dev DB per `.env`; tests use SQLite `:memory:`), Vite 8, Tailwind CSS 4, Vonage SMS

## Key Patterns

**Paint color identity = `color_code` + `color_name` on the VARIANT** (e.g. "B-1408" / "Burnt Sienna" — the manufacturer's code customers order by); `hex_code` is only a screen preview. Colour became a variant axis on 2026-09-14, alongside size and base: one product ("BOYSEN Latex Colors") carries every shade of its line, so a paint sold in forty colours is one catalogue row rather than forty. `color_code`/`color_name` are **NOT NULL DEFAULT `''`** (like `base_code`, and for the same MySQL reason — see the migration); `''` on both means "sold in no particular colour" (thinners, tools) or a custom-colour base. **Both are in the identity unique key**, not just the code: plenty of shades ship named and uncoded ("White", "Off-White"), and keying on the code alone would collapse them. `Product::$colors` appends the distinct (code, name) pairs with a hex, a label and per-shade stock — that is what the mobile colour chips read. (A normalized per-brand color library was built and reverted 2026-07-12 as too complex — see CONTEXT.md §11.)

**A product can sit in many categories** — `category_product` pivot, `products.category_id` dropped (2026-09-14). An enamel that is also a wood coating belongs in both, or customers browsing either never find it. Anything filtering by category goes through `whereHas('categories', …)`. Note the Reports "Top Categories" totals now OVERLAP: a product's revenue counts under each of its categories, so they no longer sum to the period's revenue.

**`products.name` is the product's name; `description` is a description.** Until 2026-09-14 the description doubled as the name, which left nowhere to say what the paint is for. `name` is NOT NULL, required on the form, and is what every list, alert and order line prints.

**Product images are a gallery**: `products.images` is an ordered JSON array (Filament multi-upload, drag-to-reorder, max 8); the FIRST entry is the cover. The model appends a computed `image` (= first of gallery) so single-image consumers (cart, lists, inventory thumbnails) work unchanged. Mobile product page renders a swipeable carousel with dots + counter; falls back to the hex swatch when the gallery is empty.

**Stock, price, and thresholds live on `ProductVariant`, not `Product`.** A variant is one CAN on the shelf — a **(colour × size × base)** combination, each independently priced and stocked. `Product` keeps identity only (brand, name, description, categories, images) and appends computed aggregates for API convenience (`colors` list, `size_volume` comma list, `price` = lowest variant price, `stock` = total, `stock_status` = worst case). Cart, order items, and inventory logs reference `product_variant_id`; order items snapshot `color_code`/`color_name`/`hex_code` alongside `size_volume` and `unit_price`, so recolouring or archiving a variant never rewrites a placed order (`OrderItem::$color_label` / `$display_color` are the rendered forms, and they cover custom-colour lines too).

**Variants are ordered by `sort_order`, and that is not optional.** The identity unique index is leftmost-prefixed on `product_id`, so an unordered query gets answered from it and comes back sorted by colour code — which puts every uncoded shade first. `Product::variants()` orders explicitly; the admin drags rows in the repeater to set it.

**Adjust Stock records a reason from a list** — `InventoryLog::REASONS` is keyed by action (restock / deduct / adjustment), because a supplier delivery is not a reason to deduct; `reasonOptions()` appends the free-text "Other". The preset IS the stored note, so the log never contains the literal `other`, and the lists never constrain the column — same arrangement as `Order::ADMIN_CANCEL_REASONS`. Changing the action resets the chosen reason (`afterStateUpdated`), or a deduction could carry "Supplier delivery". A reason is **required**.

**Inventory changes must go through `InventoryLog::record()`** — takes a VARIANT, atomically updates its stock and creates an audit trail with admin accountability:
```php
InventoryLog::record($variant, 'restock', 50, 'Supplier delivery');
// Valid actions: restock | deduct | order_deduct | adjustment
```

**Products use `is_archived` instead of hard delete** (variants too). The API serves the catalog via `Product::purchasable()` — active product with at least one in-stock active variant.

**Delivery orders are carried by a `driver` role with its own Filament panel at `/driver`** (design note: `DELIVERY_ROLE.md`). A driver is NOT a weaker admin — `User::canAccessPanel()` branches on `$panel->getId()`, so an admin cannot enter `/driver` either, and the driver panel discovers resources only from `app/Filament/Driver/`. The split of work: the admin picks, packs and **assigns**; the driver moves `processing → shipped` (Picked Up) and `shipped → completed` (Delivered). The admin keeps Advance / Move Back as an override for when a driver's phone dies.

- **`OrderStatusService` is the only place a status is written.** Extracted from `OrderResource` once the driver became a third concurrent actor on the same row. It holds the re-read-before-write guard and returns a `StatusChange` (moved / conflict / no_step). The guard is **optimistic, not a lock, on purpose**: a transaction would wrap `OrderObserver`'s side effects, and every queue connection is `after_commit => false`, so a rollback would leave a phantom SMS already sent. One extra status step is undoable; a text message is not.
- **`DeliveryService` owns everything driver-shaped** — assign, pick up, deliver, failed attempt, COD collection. It calls `OrderStatusService` and never writes `status` itself. Deliberately **not** an event with listeners: one publisher per action, and model events fire inside the transaction (the same trap already documented on `AdminOrderAlertService`).
- **Assignment lives on `orders`, not a `deliveries` table** — `driver_id` (who owns it now) plus `assigned_by/at`, `picked_up_at`, `delivered_at`, `delivery_note`, `failed_attempts`, `cash_collected_at`. History is `activity_logs`, which `TracksActivity` already writes; `assign()` adds a named entry because the auto-diff only records `driver_id: 3 → 7`.
- **COD cannot be delivered without confirming the cash.** Nothing else in the system ever marks a COD payment paid (`OrderController::store` writes `pending`). Confirming sets `payment_status`/`payment_date` AND stamps `cash_collected_at`, because a bare status flip cannot say *which driver* holds the money. A customer who cannot pay is **not** this path — it is Couldn't Deliver → "Customer could not pay", so no cash means no handover.
- **A failed attempt is not a status.** `failed_attempts` increments, `picked_up_at` is **never cleared** (the goods did leave the store), the order stays `shipped`, and the customer is messaged via `OrderMessageService::deliveryAttemptFailed()` — their tracker still says "on its way", so silence reads as a van that never came. Capped at `DeliveryService::MAX_ATTEMPTS` (3); at the cap the driver's button is withdrawn and `AdminOrderAlertService::deliveryExhausted()` rings the admin bell, because the decision is now the store's. **An exhausted delivery is the one `shipped` order an admin may cancel** — `OrderCancellationService::canCancel()` allows it because this is the case where the store does know where the goods are; `canCustomerCancel()` is NOT widened. **Reassigning at `shipped` returns the order to `processing` and clears `picked_up_at` / `failed_attempts`**, since the previous driver was told to bring the items back — without that the new driver inherits a spent counter and a pickup they never made.
- **Adding a role means auditing every `whereIn('role', …)`.** `User::admins()` deliberately excludes drivers (so no stock alerts, no new-order bell, never `activeAdmin()`); `Message::isVisibleTo()` correctly refuses them; `sendPasswordResetNotification()` and `ActivityLog::log()` both had to widen to `User::isStaff()` — each of those fails *silently*. All locked by `tests/Feature/DeliveryDriverTest.php`.
- A driver reaching another driver's order gets **404, not 403** — it falls out of `DeliveryResource::getEloquentQuery()` being scoped to `driver_id`, same rule as `MessageAttachmentController`.
- **Each panel refuses the other, and Filament words that refusal as "These credentials do not match our records"** — identical to a wrong password. A driver typing a correct password at `/admin/login` was told it was wrong. `app/Filament/Auth/Login.php` overrides `throwFailureValidationException()` (the failure path only, so it costs nothing on a successful login and cannot disturb rate limiting or MFA): it re-checks the credentials and, only when the password was RIGHT, names the panel they should use instead. Archived staff and customers get their own honest message. No enumeration risk — every helpful branch is behind a correct password. The invitation email now names the sign-in URL too (`StaffAccountInvited::panelLoginUrl()`).
- **`Resource::getUrl()` resolves against the CURRENT request's panel, so any cross-panel notification must pin `panel:`.** A driver's third failed attempt raised an admin alert linking to `OrderResource`, and from the driver panel that asked for `filament.driver.resources.orders.edit` — a 500 *after* the DB writes had already committed, so the order advanced and the alert vanished. `AdminOrderAlertService` (both methods) and `ProductVariantObserver` now pass `panel: 'admin'`. Any new alert raised outside `/admin` needs the same.
- **Testing a panel's login means testing the panel's CONFIGURED page class**, not `Filament\Auth\Pages\Login` — the latter quietly exercises stock Filament and passes while the override under test never runs. Also call `Filament::setCurrentPanel(...)` in any panel test: without it Filament builds URLs against the DEFAULT panel and table row actions die on `filament.admin.resources.deliveries.view`.
- **`StaffInviteService`** (was `AdminInviteService`) issues both admin and driver invitations — the token mechanism never cared about the role. The `admin_invites` table keeps its name. `AcceptInvite` must redirect by role, **not** `Filament::getUrl()`: that resolves to the panel the route is registered on, which would sign a driver in and bounce them straight back out.

**SMS notifications** via `app/Services/SmsService` use Vonage (`VONAGE_KEY`, `VONAGE_SECRET`, `VONAGE_SMS_FROM`). Deliveries are logged to the `sms_logs` table.

**Order updates are posted into the customer's message thread** by `app/Services/OrderMessageService` — an itemized summary on `orderPlaced()` (called from `OrderController::store` after commit) and a one-liner on every status change (via `OrderObserver`, so the Filament edit form, table actions, and the mobile cancel endpoint all announce alike). **Cancellation only refunds a payment that was actually `paid`.** Payments are created `pending` at checkout and the only thing that has ever marked one `paid` is a driver confirming COD cash, so writing `refunded` unconditionally told the store it had returned money it never received. A pending payment on a cancelled order stays pending; cancelled orders are excluded from every report figure by `countableOrders()` anyway. **No payment gateway is in scope** (course constraint, confirmed 2026-09-23: billing only, no collection). So nothing marks a gcash/card payment `paid` and nothing should — those rows record the method the customer CHOSE, not money received. COD is the only method that can ever read `paid`, stamped by a driver confirming cash. The Reports paid-vs-outstanding split therefore shows every online order as outstanding, which is accurate under billing-only and **is not a bug to fix**. Do not add gateway callbacks or mark online payments paid without checking this constraint still holds.

**Cancelling always goes through `app/Services/OrderCancellationService`** — one path shared by the customer's mobile cancel and the admin's Cancel action, so both restore stock, write the `order_cancelled` inventory log, refund the payment, and record `cancellation_reason` / `cancelled_by` / `cancelled_at` in a single update (the observer needs all of it at once to word the message). A reason is **required** on both sides: presets come from `Order::CUSTOMER_CANCEL_REASONS` / `Order::ADMIN_CANCEL_REASONS` plus a free-text "Other", and the stored value is never constrained to those lists. `cancelled` is deliberately missing from the admin status dropdown — leaving it there would let an admin cancel with no reason and no stock return. The customer message is worded by `Order::cancelledByCustomer()`: their own cancellation is confirmed, a store-side one apologises.

**Orders are referred to by placed-at date and time, never by id** — ids are a shared auto-increment, so a first-time customer seeing "#147" wonders what happened to their other 146 orders. Keep it that way in any new customer-facing copy. Messages are sent from `User::activeAdmin()`, which both keeps them in the normal customer↔store thread and **opens a thread for customers who never messaged first** — the admin inbox is built from existing messages, so without this those customers are unreachable. SMS is deliberately not wired up yet (no gateway subscription); `OrderMessageService::post()` carries a `TODO(sms)` marker — mirror the same `$content` there so both channels stay in sync.

**Messages carry photos, and `content` is nullable because of it** — a customer photographing the wrong shade has said everything, and a required caption is a caption nobody reads. Files live in `message_attachments` (a table, not a JSON column like `products.images`: these need a mime to refuse the unexpected, a size, pixel dimensions to lay the bubble out before the image loads, and a row identity to authorise on). `disk` is stored PER ROW so the eventual move to object storage leaves historical photos resolvable. Everything goes through `MessageAttachmentService::send()` — the one path for both the API and the Filament page — and the ordering inside it is deliberate: **files are written BEFORE the transaction**, under a ULID path that needs no message id, because a file with no row is invisible junk while a row with no file is a permanently broken photo in a customer's thread. The catch block deletes files on a failed transaction; `messages:prune-orphan-attachments` is the actual guarantee, since a fatal runs no catch block and a DB-level cascade (`users` → `messages` → `message_attachments`) fires no Eloquent events at all. **No HEIC** — Chrome cannot display it, this server has gd and no imagick so it cannot even be measured, and the app re-encodes every pick to JPEG so it never arrives. `content` being nullable means every surface that prints a message as ONE LINE must go through `Message::preview()`; three do (API conversations, admin sidebar, mobile bubble).

**Attachments are never served from a storage path** — `MessageAttachmentController` is reached by an API route (Sanctum) and a panel route (registered in `AdminPanelProvider`, like `reports/print`), same gate both ways: sender, receiver, or any admin. It answers **404, not 403**, for a refusal — ids are a plain auto-increment, so a 403 on a row that exists is a difference anyone can measure by counting. On an S3 disk it redirects to a 5-minute `temporaryUrl`; that URL outlives the check that issued it, which is the trade for not proxying every photo through PHP.

**`messages.kind`** separates what the store TYPED from what the system POSTED (`chat` / `order_update`); `OrderMessageService` sets the latter and both clients draw it as a card, not as a bubble from a person who never wrote it. History is deliberately **not** backfilled — recognising an old order update means pattern-matching free text, and an admin who once typed something similar would be miscategorised with no way to tell.

**A new order rings the admin bell** — `app/Services/AdminOrderAlertService::orderPlaced()`, called from `OrderController::store` right after `OrderMessageService::orderPlaced()` and AFTER the commit. Deliberately not an observer: `created` fires inside the transaction (a rollback would have admins chasing an order that never existed), and an order an admin types into the Filament create form would ring that admin's own bell. Same `notifyNow` rule as the stock alerts. The customer's half of that moment is the message thread; this is the store's half.

**Stock alerts** are two coordinated pieces (see CONTEXT.md §6 for detail):
- `app/Observers/ProductVariantObserver.php` — on any variant stock update, alerts all admins via the Filament notification bell, but **only on downward severity transitions** (in stock → low → out); never on restock
- `app/Listeners/SendStockAlertsOnLogin.php` — on admin login, shows an instant popup briefing of current stock state and mirrors it in the bell, replacing the previous briefing (identified by `data->title`) so it never stacks
- Both deep-link to `InventoryResource` — its Stock Status filter's `attention` option is the landing target; **do not remove it**
- Use `$user->notifyNow($notification->toDatabase())`, NOT `sendToDatabase()` — the latter silently queues and requires a running worker
- Filament gotchas: table-filter deep links use `?filters[...]` (not `?tableFilters`); notification bodies render as sanitized HTML (use `<strong>`, not markdown)

## Filament Admin (`app/Filament/`)

Resources auto-discovered from `app/Filament/Resources/`:
- **ProductResource** — name, brand, multi-select categories, image upload; variants Repeater ("Colors & Sizes": colour name/code/hex + size/base/price/threshold; collapsible, cloneable, drag-reorderable into `sort_order`; initial stock is create-only — afterwards stock moves through Inventory); Archive/Unarchive action. Row uniqueness is validated on the whole (colour, size, base) combination — `->distinct()` on one column would reject legitimate rows

**Getting a hex into the product form** — under the color picker sits a "Pick color from an image" tool (`resources/js/filament/color-from-image.js` + `resources/views/filament/forms/color-from-image.blade.php`): drop/paste/browse a photo, click it to sample a 5×5 average with a magnifier loupe, or take one of the auto-extracted dominant swatches; a "Sample from screen" button uses the native `EyeDropper` API where it exists (Chrome/Edge). Everything is client-side canvas work — **no upload, no storage, no server round trip** except the single `$wire.set(…)` that hands the colour back. Since 2026-09-14 the tool sits INSIDE each variant row (colour moved onto the variant), so there is one per shade and the target path is `data.variants.<uuid>.hex_code` — the blade derives it from its own state path, so this needed no JS change. Notes for changing it:
- It is registered as a Filament `AlpineComponent` in `AppServiceProvider`, so `php artisan filament:assets` must publish it — that already runs on every `composer install` via `filament:upgrade`
- The admin panel compiles no custom Tailwind theme, so app views **cannot use utility classes**; this one ships its own scoped `<style>` (including an `[x-cloak]` rule, which Filament's CSS does not provide)
- Writing the sibling `ColorPicker`'s state path works because its input is `x-model="state"` and `state` is entangled — do not reach into its Alpine internals
- A photo is not a colour measurement (white balance, lighting). Fine for `hex_code`, which is only a screen preview; never present it as reading the true paint colour
- **OrderResource** — status moves **one step at a time along `Order::STATUS_FLOW_BY_TYPE`**, not by dropdown: an "Advance" button naming the next step (`STATUS_ADVANCE_LABELS`), plus a one-step **Move Back** for a press that went too far. Both on the row and the edit header; the edit form shows status read-only. The old dropdown offered every status regardless of type, so a delivery could be set `ready_for_pickup` — which the app's per-type tracker cannot place, leaving the customer looking at an order that still says "Order Placed". Mirrored by `FLOW` in the mobile `constants/orders.js`; keep the two in step. Both actions re-read the record before writing, because the table polls and two admins can hold the same row. Cancelling is still its own action; table polls every 30s and the sidebar carries a **pending-orders badge**. Badges render with the sidebar, so the badge only refreshes on navigation — the bell is the live signal
- **UserResource** ("Admin Accounts", super admin only) — no password field on either create or edit; status is three-valued (Active / Pending invite / Inactive); row actions Resend invite (pending only) and Set password manually
- **BrandResource / CategoryResource** — simple CRUD
- **InventoryResource** — ProductVariant-backed stock management, one row per size (Adjust Stock / View Logs / Set Alert actions); worst stock sorts first; `attention` filter option is the notification deep-link target

**Save closes the form and returns to the table** on products, brands and categories (`app/Filament/Concerns/ReturnsToTableAfterSave`, used by both the create and the edit page). This reverses the earlier "no auto-close" behaviour (two traits that held the form open, removed 2026-09-15): finishing a record and landing back on the list is what was wanted. The trait names the index URL outright rather than leaning on Filament's default, so a panel-wide `resourceCreatePageRedirect` / `resourceEditPageRedirect` set later cannot silently move it.

**Admin accounts are claimed, never handed over.** Creating one in `UserResource` sets a random 64-char password nobody ever sees and emails an invitation *link* (`AdminAccountInvited`); the invited person chooses their own password at `/admin/invite/{token}` (`app/Filament/Auth/AcceptInvite.php`, registered under the panel's **guest** `routes()` — `authenticatedRoutes()` would redirect them to a login they cannot pass). **The email never carries a password.** `AdminInviteService` is the only path: `issue()` mints, `send()` mails, `accept()` claims. Notes:
- **`admin_invites` is deliberately NOT `password_reset_tokens`.** A panel has exactly one broker (Filament's reset page hardcodes `Password::broker(Filament::getAuthPasswordBroker())`), so a second broker configured with a longer invite expiry would have its tokens judged by the panel broker's expiry anyway; the reset table is keyed by email and `deleteExisting()` wipes the row on every `createToken`, so an invite and a reset would clobber each other; and the broker knows nothing about **account state**. That last one is the real reason — see below.
- **An unclaimed account is not a person yet.** It is `role=admin, is_archived=false` and otherwise indistinguishable from a working admin. `accepted_at` is what makes it knowable: the table shows a third status (**Pending invite**, amber) and `User::activeAdmin()` skips it — otherwise an account nobody has ever signed into becomes the sender of every automated order message, and the admin inbox parks those threads under it. Reachable as soon as older admins are archived.
- Invites last **72 hours** (`AdminInviteService::EXPIRY_HOURS`); password *resets* keep Laravel's 60 minutes, because that flow starts with the person already at the keyboard. One invite row per user — a reissue rewrites it, so the old link dies and there is never a question of which invite is live. Token stored as plain `sha256` (looked up *by* token; bcrypt would mean a table scan).
- **Resend is hidden once the account is claimed** — reissuing would blank a working admin back to pending and lock them out until they clicked. **"Set password manually"** (super admin only) is the escape hatch, and the only place a password is ever typed for somebody else; it exists because `MAIL_MAILER=log` means no invitation actually reaches an inbox yet. It stamps `accepted_at` too, or the account would keep reading as pending. **The panel never claims an invitation was sent unless it was.** `AdminInviteService::send()` returns an `InviteDelivery` with three outcomes — **sent**, **failed** (transport threw), **notMailed** (`MAIL_MAILER=log`: no error, no recipient either). `UserResource::inviteNotification()` renders all three from one place so the create page and the resend action cannot drift. Only the first is green; the other two are amber, say plainly that nothing was sent, and **print the link**, because it is then the only way left to get that person in. A green "sent!" over a mail that threw is how a super admin walks away believing a colleague was contacted while that colleague waits for an email nobody posted. A **failed send never rolls back the account or the invite** — they are committed first, so a dead mail server costs a resend, not a re-keyed record, and the invite stays pending which is what keeps the Resend action on screen.
- **Password reset is vanilla Laravel** (`->passwordReset()`), gated in `User::sendPasswordResetNotification()`: it silently returns for customers and archived admins. Customers share the `users` table, so without it a customer's address typed into the panel's forgot-password form gets emailed a link into the admin panel. Silent rather than erroring, so the form cannot be used to enumerate which addresses are admins. The super admin's only route is this one — `UserResource` filters to `where('role', 'admin')`.
- **A page behind `routes()` must ALSO be listed in `->livewireComponents([...])`.** Routing to the class renders the first GET fine, but every interaction after that is a POST to `/livewire/update` that resolves the component **by name** — and a class reached through `routes()` is registered under no name, so submitting the form dies with `Unable to find component: [app.filament.auth.accept-invite]`. Filament registers its own auth pages (login, password reset, profile) this way; anything you add yourself has to say so. Note `Livewire::test()` takes the class directly and a `get()` only exercises the first render, so **neither catches this** — the regression test resolves through `ComponentRegistry::getClass()` instead.
- **`->profile(EditProfile::class, isSimple: false)`** needs the custom page in `app/Filament/Auth/EditProfile.php`: Filament's stock form opens with a single `name` field, and `name` here is an appended accessor over `first_name`/`last_name`, not a column. Left alone it renders a populated field that saves nothing and still reports success.

Custom pages: `Dashboard`, `Messages`, `Reports`

**Reports is built from one payload, rendered three ways.** `ReportBuilder::make($period, $sections, $options)->build()` is the only thing that queries; the Livewire page, the printed document (`/admin/reports/print`) and the CSV export (`/admin/reports/export/{section}`) all consume that same array. Section partials in `resources/views/reports/sections/` are shared by screen and paper and **must never query** — a test fails the build if one references a model, `DB::` or a query method. This replaced a page that computed ~15 aggregates inline and then restated every one of them in a second, print-only copy of the markup.

- **`ReportMeasure` defines the words.** Two revenue measures, deliberately named apart: **order revenue** (`orders.total_amount`, the headline) and **line revenue** (`SUM(order_items.subtotal)`, the only revenue attributable to a product/colour/category). They are equal today *by construction* and that equality is asserted by test — the day an order-level charge (delivery fee, discount) appears, the test fails and forces a decision instead of every attribution report silently drifting. `countableOrders()` is the single status gate (cancelled excluded, pending included) and every period figure is anchored to `orders.created_at`. The old page divided cancelled-excluded revenue by a cancelled-included order count, understating AOV by the cancellation rate.
- **Mixed cans roll up by dimension, and the asymmetry is deliberate.** A custom mix is several `order_items` rows sharing a `mix_group`. **Revenue and quantity roll up to the group** (revenue summed once at group level, quantity from the `mix_role = 'base'` row — the tint pints are not extra cans). **Stock movement does not roll up**: a tint consumed inside a mix really left the shelf, so dead-stock and sell-through count those rows individually. `ProductMetrics` therefore does *not* roll up while `ColorMetrics` does, and both still reconcile to line revenue.
- **Period vs point-in-time is a property of the metric.** Stock levels, open orders and customer totals describe *now*, are never compared against a past window, and render with an as-of stamp — a live pending count printed under a letterhead naming last month is simply false.
- **Granularity is suggested, never imposed.** Day / week / month / quarter / year. `ReportPeriod` is immutable (`withGranularity()` returns a new instance); an explicit choice always wins and the toolbar shows "Auto (Week)" vs "Week". Too many buckets warns, it does not override — a silent downgrade once drew a whole month as a single dot. Auto escalates by span (≤31d day, ≤182d week, ≤3y month, ≤10y quarter, else year) so a long range never draws hundreds of points. Two consequences of the coarse steps: a range not starting on a bucket boundary produces a **partial** first/last bucket — one labelled "2026" holding eleven months reads as a full year, so the report says so — and a chart of **3 points or fewer renders as bars**, because a line draws a trend between marks that have none.
- **Charts: one y axis, ever.** Revenue and orders are two charts side by side, never a second axis. With a comparison the default is **split** — each period gets its own date axis, locked to a **shared y ceiling** (overlaying plots the comparison against the *current* period's labels, which is wrong whenever the two windows differ in length). Chart specs are built in PHP (`ReportCharts`) and dispatched to the browser, because the canvases sit behind `wire:ignore` and their `data-chart` attributes never update — reading the DOM redrew the previous grouping. The canvas is pinned `position:absolute` inside an `overflow:hidden` wrapper; without that Chart.js's own inline sizing painted over the next section.
- **Print is its own document**, not `window.print()` on the panel — so there is no dark-mode kill switch and charts actually print. Page-break policy is declarative (`ReportSection::$pageBreak`): short sections keep themselves whole, long ones flow and fill the page. A blanket `break-inside: avoid` left half-empty pages *and* stranded headings, since a section taller than a page has to break somewhere. Page furniture uses `@page` margin boxes with `counter(page)`/`counter(pages)`, which Chrome does support.
- **Presets store configuration, never figures**, versioned `{"v": 1}`, with the date range saved as a *rule* (`last_30_days`) rather than two dates — otherwise "Monthly Owner Report" needs its dates re-picked every month. Unknown section keys are dropped on load so a rename never bricks a saved preset. **CSV exports raw numbers** (`1031.6`, not `₱1,031.60`) with a UTF-8 BOM, because a formatted figure lands in a spreadsheet as text no formula will touch.

`Messages` has a **New** button (compose mode) that lists non-archived customers with a search box, so an admin can write first; the conversation sidebar itself is derived from existing messages and can only ever show customers who already have one.

Widgets: `StatsOverview` (today's sales 7-day chart, pending orders, low/out-of-stock counts), `LowStockWidget` — **both must be listed in `Dashboard::getWidgets()`**, which replaces Filament's discover-everything default; a widget left out of it renders nowhere while still passing a page-loads smoke test (LowStockWidget was in that state until 2026-09-15). Both poll at 30s, as do the Orders and Inventory tables — `StatsOverview` would otherwise inherit Filament's 5s, which is ten aggregates a tick

## REST API (`routes/api.php`)

**Public:** `POST /api/auth/register|login` — **register requires `phone`** (PH mobile, `/^(\+?63|0)9\d{9}$/`), because order updates go out by SMS and `OrderController::store` silently skips sending when it is null; spaces and dashes are stripped before validating so `0917 123 4567` is accepted. `address` stays nullable — checkout already demands one for delivery orders, and requiring it would block pickup-only customers. `GET /api/products` (filters: search, brand_id, category_id, price range; `search` matches product name OR description OR any active variant's color_code/color_name, with Unicode dashes normalized; `category_id` matches the pivot), `GET /api/products/{id}`, `GET /api/brands` (catalog brand grid: only brands with purchasable products, `products_count` = purchasable only, includes `image` logo), `GET /api/brands/{brand}/categories` (category chips for a brand's list, purchasable counts), `GET /api/categories`

**Customers have no password recovery — not on any channel.** There is no forgot-password endpoint, no reset email and no SMS equivalent; a customer who forgets their password is locked out permanently. Deliberately left out of the admin-invite work (2026-09-22) rather than fixed halfway. Building it is its own task: the `users` table is shared, so whatever is added must not become a second way into the admin panel, and the phone-OTP machinery in `AuthController` (`otp_verifications`, hashed codes, attempt caps) is the closer precedent than Laravel's email broker.

The mobile catalog is **brand-first**: landing shows a brand grid (logo tiles; lettered fallback), tapping opens `brand/[id]` with that brand's products; the search bar is global and bypasses the grouping.

**Protected (`auth:sanctum`):** `GET /api/badges` — the two integers behind the app's tab badges (`unread_messages`, `cart_items`); polled by `(tabs)/_layout.jsx` every 60s, and pushed without a round trip by anything that already knows the answer (every cart endpoint returns `item_count`; fetching a thread marks it read). Its unread predicate must stay identical to the one `MessageController::thread()` marks read with, or the badge never clears. cart CRUD (`POST /cart/add` takes `product_variant_id`; update/remove are keyed by `cart_item_id`), order create/list/show/cancel (`POST /orders/{order}/cancel` **requires** a `reason` string), messages send/read/thread (**`POST /messages/send` is multipart** — `attachments[]`, max 5 photos, 8 MB each, jpg/png/webp; `content` is `required_without:attachments`), `GET /messages/attachments/{attachment}` (auth-gated, 404 on refusal), `POST /api/auth/logout`, `GET /api/auth/me`

`POST /api/orders` accepts an optional `cart_item_ids` array — the Shopee/Lazada-style partial checkout. Only those lines are ordered and removed from the cart; unticked lines stay. Omitting it checks out the whole cart (previous behaviour).

**`payment_method` must fit the `order_type`** — `Order::PAYMENT_METHODS_BY_TYPE` is the one source of truth, enforced in `OrderController::store` and mirrored by `METHODS_FOR` in the mobile checkout (which only decides what is SHOWN). Delivery → `cod`, `gcash`, `card`; pickup → `gcash`, `card`. **`cash` (Cash on Pickup) is no longer offered at all** (QA, 2026-09-14): a pickup that costs nothing to place and nothing to abandon is free to spam while its stock sits reserved for someone who never comes. It stays in the `payments.payment_method` enum so existing orders still read back — do not remove it from the enum, and do not put it back in either list.

Product JSON includes an `active_variants` array (id, color_code, color_name, color_key, color_label, hex_code, size_volume, base_code, price, stock, stock_status) plus an appended `colors` summary. The mobile product page picks a COLOUR first (chips from `colors`), then shows only the sizes that shade is stocked in (`active_variants` filtered by `color_key`) — a shade is not stocked in every size, and offering the product's sizes would promise cans that do not exist. Checkout locks and deducts stock per variant.

**Order JSON names the driver once the order has left the store** — appended `driver_contact` is `{name, phone}` for a `shipped` or `completed` delivery and `null` otherwise, because an assignment can still change while the order is being packed and naming a driver who is then swapped is worse than naming nobody. `driver_id`, `assigned_by` and `cash_collected_at` are in `Order::$hidden` (serialization only — the panel and services still read them normally). `failed_attempts`, `delivery_note`, `picked_up_at` and `delivered_at` are deliberately NOT hidden: the app dates the tracker from the last two and explains a missed attempt from the first two. Both order endpoints eager-load `driver` or the accessor fires a query per row.

**The delivery address is three things, not one** (see `DELIVERY_ROLE.md` Phase 5). `shipping_address` is free text handed to a map SEARCH; `delivery_landmark` is directions for a human ("green gate, near ABC Store") and is deliberately **never** fed to the map query, because it only makes a geocode worse; `delivery_lat`/`delivery_lng`/`location_accuracy` are the customer's optional GPS pin. The driver's Navigate link targets the **pin** when there is one and the address string otherwise — a real street address still resolved to the wrong part of the barangay, because "Brgy. Poblacion, Pilar" is a polygon, not a doorstep. **No map SDK anywhere**: only the Google Maps query changes.

- **Checkout now saves the address, landmark and pin back to `users`.** They were previously written to the order only, so `users.address` was fixed at registration and a customer who typed a better address had it forgotten — they retyped something short every time. `users.address` therefore now means "last delivery address used". A **pickup never touches it** (blanking a saved address because someone collected at the counter would lose it), and **ordering without a pin never wipes a saved pin** — someone who pinned home last month and orders from work this month is right to skip it.
- **Accuracy is stored and shown, never promised.** A fix taken indoors can be a ±500 m cell-tower estimate. Every surface quotes the reported figure so a vague pin is not mistaken for a doorstep — the same rule that stopped us geocoding "Pilar, Bataan".
- **Accuracy is NOT correctness.** It says how precisely the phone was located, never whether the phone was at the delivery address: a contractor ordering for a job site gets a ±8 m pin on their own office and every check passes. That is why the confirmation asks *"Is this where the order should be delivered?"* and shows the reverse-geocoded place name, and why the button says "Use my current location" rather than "Pin my address".
- **The pin is optional and never nagged.** Declining leaves the customer exactly where they were — a text address. `expo-location` is a **native module**, so it needs `expo run:android`, not a Metro reload; background location is explicitly disabled in `app.json`.
- A half-sent coordinate is rejected (`required_with` on the pair) — one field lost to a flaky connection would otherwise be stored as a pin on the equator. An unpinned delivery hands the app `null`, never `0`: 0,0 is a real place in the Gulf of Guinea.

**Driver endpoints live under `/api/driver`** (`DriverDeliveryController`), behind `auth:sanctum` **and** the `driver` middleware alias (`EnsureUserIsDriver`, registered in `bootstrap/app.php`). The namespace gate answers **403** — it reveals nothing, unlike a specific delivery that is not yours, which still **404s** from the scoped query. Every endpoint is a thin wrapper over `DeliveryService`, the same service the `/driver` Filament panel calls, so the app and the panel cannot drift on ownership, COD cash or the attempt cap. Responses are **shaped, not model dumps** — a driver receives the customer's name, phone, address and items, never their email or `assigned_by`. `GET /api/driver/failure-reasons` hands the app `DeliveryService::FAILURE_REASONS` and `MAX_ATTEMPTS` so the two lists cannot diverge. A 409 means the store moved the order underneath the driver; a 422 means a rule refused.

Controllers in `app/Http/Controllers/Api/` (Auth, Product, Order, Cart, Message).
